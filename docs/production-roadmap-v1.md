## Phase 1: 成功率改善 — コアアルゴリズム調整（Day 2-4）

※最も重要。69% → 85%+ を目指す

### [P1-1] ノイズ耐性の改善（最重要）

**問題の本質**  
シミュ結果から、失敗時の正解ランクが平均1,232位。  
ノイズ4-5回で「完全に迷子」になる = 1回のノイズの影響が大きすぎる

**対策A: bayesianEpsilon の引き上げ**

- 現在: 0.05 → 提案: 0.08〜0.10
- 効果: YES/NOの尤度比が下がり、1問の影響が減る。1回のノイズ回答でconfidenceが崩壊しにくくなる
- トレードオフ: 情報効率は下がるが、ロバスト性が上がる
- 工数: config変更のみ → シミュで検証

**対策B: PROBABLY_YES/PROBABLY_NO の尤度調整**

- 現在: L=0.7/0.3（固定）
- 提案: ユーザーが「たぶん」と答えるケースをノイズ軽減に活用。シミュレーターの曖昧さがPROBABLY系に変換されている場合、この値を0.6/0.4に緩めることでノイズ耐性向上
- 工数: `weightUpdate.ts` を1行変更 → シミュ検証

**検証方法**  
同じ100件で `ambiguityLevel=3` のシミュを回し、`epsilon=0.05/0.08/0.10` を比較

### [P1-2] 強制Confirm の見直し

- 現在: `qForcedIndices: [6, 10, 17]`
- 提案: `qForcedIndices: [10, 20]`
  - Q6の強制を削除（confidenceが低い段階でのConfirmは無駄弾）
  - Q17→Q20に後ろ倒し
- 工数: config変更のみ → シミュ検証

### [P1-3] maxQuestions の動的拡張

- 現在: `maxQuestions: 30`（固定）
- 提案: 基本30問。ただしconfidence 0.3以上なら35問まで延長
- 工数: `answer/route.ts` に条件分岐を数行追加
- 使用モデル: Auto
- 理由: 「あと少しで当たりそう」なケースを救済

### [P1-4] 有名度プライオリの有効化

- 現在: `alpha: 0`, `playBonusOnSuccess: 0`
- 提案: `alpha: 0.02`, `playBonusOnSuccess: 1`
- 工数: config変更のみ → シミュ検証
- 注意: alpha の効果はシミュではノイズに対する直接の改善にはならないが、有名作品の早期収束を実現し「体感成功率」を上げる

### [P1-5] REVEAL閾値の動的調整

- 現在: `revealThreshold: 0.7`（固定）
- 提案:
  - Q1-15:  0.7
  - Q16-20: 0.6
  - Q21-25: 0.5
  - Q26-30: 0.4
- 工数: `answer/route.ts` のREVEAL判定に段階的閾値ロジック追加
- 使用モデル: Auto
- 理由: 「早めに当てに来て、外れたらもう少し聞く」体験の実現。30問で打ち切りになるくらいなら、低い閾値で当てに行くべき

**Phase 1 の検証サイクル**

1. P1-1（epsilon調整）をまずシミュ → 最も効果的な値を決定
2. P1-2（強制Confirm見直し）を追加 → シミュ
3. P1-3, P1-5（maxQ + 動的REVEAL）→ シミュ
4. 全部込みで最終シミュ → 成功率 85%+ を確認

目標: Day 2-4 で 4-5回のシミュサイクルを回す

### Opus回答（実装・設計の詳細）

#### Phase 0

**#1: SessionManager 楽観的ロックの実装方針**

- 現在の実装（`src/server/session/manager.ts` 138-170行）: getSession → マージ → update で全フィールド上書き。1と3の間に別リクエストが割り込むと Lost Update。
- 実装方針:
  1. getSession() で updatedAt も取得
  2. 処理実行
  3. update の where に `updatedAt` を条件追加
  4. 更新行数が0なら409エラー
- Prisma の update は where に sessionId のみなので、**方法B（version カラム追加）を推奨**。`version: { increment: 1 }` + where で版数チェック。Prisma ネイティブで完結。

**#6: 7日以上の根拠**

- 7日は目安。1セッション=1ゲーム、通常5-30分で完了。途中中断でも2-3日。7日以上前は「放棄」とみなす。
- 現在セッション有効期限の概念はない。`updatedAt` が7日以上前のレコードを削除。
- 「昨日の続き」を考慮するなら3日に短縮しても可。

#### Phase 1

**#7: 正解ランク平均1,232位の前提**

- 同じ100件シミュの `failureAnalysis` から取得。失敗31件のみの平均（成功69件は含まない）。
- `avgCorrectRank: 1232.68` = 失敗ケースで正解が5,386作品中1,232位。`avgTop1Confidence: 0.1027`、`avgWasNoisyCount: 4.39`。

**#8: bayesianEpsilon の設定場所**

- `config/mvpConfig.json` の `algo.bayesianEpsilon`。現在 0.05。0.08 等に変更するだけ。

**#9: PROBABLY の尤度設定場所**

- `src/server/algo/weightUpdate.ts` の `getLikelihood` 関数（35-41行）。0.7/0.3 がハードコード。config化するか直接変更。

**#10: 0.6/0.4 に緩めるの意味**

- その理解で正しい。差を 0.4 → 0.2 に小さくする = ノイズ耐性向上。
- **順序**: まず epsilon を変えてシミュ。足りなければ PROBABLY も調整。

**#11: qForcedIndices の設定場所**

- `config/mvpConfig.json` の `confirm.qForcedIndices`。現在 `[6, 10, 17]`。

**#12: Q6 を外した場合のリスク**

- リスクは低い。Q6 で confidence 0.25 以上になるのは alpha=0 の現在ではほぼ起きない。Q6 強制は「無駄弾」状態で発動している。外しても confidenceBand の自然発動で拾える。

**#14: 35問延長のトリガー**

- **30問到達時に判定**。途中から35問前提にはしない。
- 実装イメージ: `if (questionCount >= maxQuestions) { if (confidence >= 0.3 && questionCount < 35) { 延長 } else { FAIL_LIST } }`
- 場所: `src/app/api/answer/route.ts` の MAX_QUESTIONS 判定部分。

**#17: Q26-30 で閾値 0.4 の誤REVEALリスク**

- リスクはあるが `maxRevealMisses: 3` で安全弁あり。外すとペナルティ適用、3回で FAIL_LIST。
- 0.4 で REVEAL = top1 が40%以上。40%で当たる確率なら3回中1回は78.4%。
- 誤REVEALは増えるが「外しても再挑戦」の体験は悪くない。気になるなら 0.45 から始めても可。

#### 全体

**#38: 成功率85%の評価タイミング**

3段階で評価:

| タイミング | 対象DB | 目標 |
|------------|--------|------|
| **1. Phase 1 完了時（Day 4頃）** | 現在の5,386作品 | 85%+ (ambiguity=3) |
| 2. DB 8,000作品到達時（Day 7頃） | ~8,000作品 | 80%+ |
| 3. DB 10,000作品 + 本番直前（Day 9-10） | ~10,000作品 | 80%+ |

- 作品が増えると成功率は自然に下がる（log₂ で約1ビット分の負荷増）。
- **タイミング1が最重要**。5,386作品で85% → 本番10,000作品で80%前後が許容範囲。
