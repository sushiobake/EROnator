# タグチェック API 設計メモ

タグチェックに関する経緯・課題・方針を一箇所にまとめたドキュメント。大きな問題であり、議論の整理と現実的なコスト試算が必要。

**更新日: 2026-02-19**

---

## 1. そもそもの流れ

- **Cursor エージェント**で「タグ付け」「タグチェック」をそれぞれ依頼していた
- **auto** だと安定性に欠ける → **GPT 5.1** で 100 件ずつ試行
- **100 件の理由**: 5 万件達成までコピペ回数を減らすため。最低でもそれくらいはやれないと負荷が大きい
- **理想**: 10 件×5,000 回の自動化（未達）
- **タグ付け**: やや安定しそうに見える
- **タグチェック**: ミスる、サボる、止まる

---

## 2. API を使う場合のメリット・デメリット

| メリット | デメリット |
|----------|------------|
| 1件ずつ自動化できる（1×100 やそれ以上に拡張可能） | 毎回タグリストを送るのか？ |
| 1件ずつならサボる流れにならない | トークン数は？ |

### 人間の流れとの対比

- **人間**: 最初にタグリストを覚える → 整合性で追加提案
- **API**: 1回ごとに読ませる → 非効率 → トークン増

### 矛盾点

**まとめてやるとサボる**という問題がある一方、**小さくするとトークン効率が悪化**する。  
バッチ大きくすると品質低下、小さくするとコピペ回数・トークンコストが増える。

---

## 3. 現状の実装とトークン内訳

### 実装

- [src/app/api/admin/groq-check-one/route.ts](src/app/api/admin/groq-check-one/route.ts): チェック待ちから 1 件取得 → 指示書 + 作品データ（allTags 含む）を **1 本のプロンプト**で Groq に送信
- タグリスト（allTags）は DB から取得し、毎リクエストでプロンプトに含めて送っている

### 実際のエラー（413）

- **Requested 9,163 tokens**（Groq 無料枠 TPM 6,000 超過）

### 内訳（推定）

| 内容 | トークン |
|------|----------|
| 指示書（check-instruction-1item.md） | 2,500〜3,500 |
| 作品データ（allTags 以外） | 500〜1,500 |
| **allTags（s/a/b フル）** | **4,000〜6,000 以上** ← 大半 |

---

## 4. 5万件のコスト試算

**仮定**: 入力 10,000 トークン/件、出力 800 トークン/件  
→ 50,000 件で 500M 入力、40M 出力

| API | 50k件の概算 | 備考 |
|-----|-------------|------|
| DeepSeek | 約 $157 | 安い、キャッシュでさらに削減可能 |
| GPT-4o-mini / Groq 120B | 約 $99 | バランス良い |
| Groq 70B | 約 $327 | 既存統合が楽 |

**結論**: 5万件で $100〜300 程度は**現実的**。非現実的ではない。

---

## 5. トークン削減の選択肢

| 案 | 内容 | トレードオフ |
|----|------|--------------|
| A. allTags を一部に制限 | s/a/b を 80/60/60 などにスライス | 追加候補が後半にあると見逃す |
| B. プロンプトキャッシュ | 指示書 + allTags をキャッシュ（DeepSeek 等） | 同一プレフィックスでキャッシュヒット、変動分のみ課金 |
| C. 指示書を縮める | ルール削減 | チェック品質低下（**非推奨**） |

## 9. gpt-5-nano の empty content：2件 vs 10件の差（2026-02-20）

### 現象

- **2件**を選ぶと成功
- **10件**を選ぶと「さっきと同じエラー」（Phase0 失敗）が出る

### なぜか

BATCH_SIZE=2 のとき：

- 2件 → **1回**の API 呼び出し（2作品）
- 10件 → **5回**の API 呼び出し（各2作品）

リクエストあたりの作品数は同じ（2作品）。違うのは **呼び出し回数** と **扱う作品の組み合わせ**。

1. **試行回数**: 1回なら失敗しなくても、5回あればそのうち1回は失敗しやすい
2. **作品の長さ**: 10件には `commentText` が長い作品が含まれている可能性が高い。そのようなペアだとプロンプトが大きくなり、推論トークンが膨らんで empty content になりやすい
3. **選ばれ方**: 2件時は先頭2作品、10件時は 5 ペア。後半のペアに「長いあらすじ」の組み合わせが来ると、そのチャンクだけ失敗する

### 結論

たまたまではなく、**10件 = 5回の試行** なので、1回以上失敗する確率が高く、かつ長い作品が含まれるチャンクで失敗しやすい。2件のときは「たまたま軽いペア」だった可能性が高い。

### 対策案

- BATCH_SIZE を 1 にして 1 作品ずつ送る（失敗率低下、コスト・リクエスト数増）
- empty のときにリトライする
- gpt-5-mini に切り替える
